Authoritative architecture record for the FarmCore assistant and document-retrieval
track. It defines the runtime shape, the knowledge sources the assistant may draw
on, the boundaries it must not cross, and the contracts other teams build against.

### 1.1 In scope

This document is normative for the following.

|---|---|

| Retrieval | Physical storage, logical indexes, the `RetrievalScope` contract, hybrid recall, reranking, diversity |
| Authorisation of knowledge | Where farm/role scoping is enforced relative to retrieval and generation |
| Assistant orchestration | Stage sequence, tool invocation order, groundedness gating, refusal taxonomy |

| Audit | Audit as a pipeline stage, the event shape, and the version-pinning tuple |

### 1.2 Explicitly out of scope

| Excluded | Why | Who owns it |
|---|---|---|
| **FarmFlow task placement** | Scheduling is deterministic and must remain reproducible from approved structured inputs. The assistant may *request* a proposal and *explain* a result; it never decides a slot, a resource assignment, or an ordering. | Scheduling team (`scheduling` app) |
| **UI templates, HTMX fragments, static assets, map rendering** | The assistant track produces JSON contracts and server-side services. Presentation is a separate ownership boundary. | UI team |
| Deployment platform, hosting provider, CI runner selection | Undecided until the local Compose stack is stable; not an AI-track decision. | Project lead |
| Identity provider, JWT, SSO | POC uses Django session auth with a custom email user model. | Accounts / project lead |
| Vector database migration (Qdrant or otherwise) | pgvector is the accepted POC choice. A change requires the evidence-based comparison recorded in the decision checklist. | Assistant team, gated |
| Cross-session durable chat history | Client scope requires current-conversation context only. Persistence is an assistant-team implementation choice, not an architectural requirement. | Assistant team |
| DOCX ingestion and image OCR | Deferred for the POC; PDF and text only. | Documents team, deferred |

Anything not listed as in scope is not settled by this document. Do not infer a
decision from silence — raise it as a checklist item.

## 2. Design Principles

These are the seven rules that resolve disputes. When a local design choice
conflicts with one of these, the principle wins or the principle changes by ADR.

### 2.1 Contracts-first

No module consumes another module's internals. Every cross-team surface is a
declared contract before it is an implementation:

- HTTP contracts are DRF serializers, with OpenAPI generated by `drf-spectacular`.
  Serializers are the single source of truth; there is no parallel shared-types
  package.
- In-process contracts are named service functions exported by a Django app
  (`documents.services.search_documents`, `assistant.services.answer_message`).
  Other apps call those functions. They do not import models across app
  boundaries or write another app's tables.
- Data contracts (chunk records, snapshot manifests, audit events) have a
  versioned schema and a validator. A producer that cannot satisfy the validator
  fails loudly rather than emitting a partially-valid record.

A contract may be stubbed before it is real. A stub that returns a typed, schema-
valid empty result is a legitimate integration point; an undefined function
signature is not.

### 2.2 Ports and adapters for everything external

Every external dependency is reached through a narrow port owned by one Django
app. Adapters are swappable; call sites are not rewritten when a provider changes.

| Port | Owner | Operations | POC adapter |
|---|---|---|---|
| `EmbeddingPort` | `assistant` | `embed_documents`, `embed_query` | Local/open-weights embedding model, dimension pinned before schema migration |
| `GenerationPort` | `assistant` | `generate`, `generate_structured` | Team-selected LLM; provider experimentation stays behind this port |
| `RerankPort` | `assistant` | `rerank(query, candidates) -> scored` | Cross-encoder reranker; degrades to identity ordering |
| `EntailmentPort` | `assistant` | `entails(claim, evidence) -> bool, score` | Small NLI model, or judge prompt through `GenerationPort` |
| `ExtractionPort` | `documents` | `extract_text`, `extract_tables` | PDF text/table extraction, no OCR in POC |
| `ObjectStorePort` | `documents` | `put`, `get`, `presign`, `stat` | MinIO (S3-compatible) |
| `WeatherPort` | `farms` | `fetch_forecast(point, days)` | Free forecast provider, normalised to the POC weather contract |

Rules that make the abstraction real rather than decorative:

- Provider SDK types never escape the adapter. Ports exchange plain FarmCore
  dataclasses.
- Credentials live in adapter configuration only. No other layer reads a provider
  key, and the model never receives one.
- Ports are the only place retries, timeouts, and circuit-breaking are
  implemented, so failure posture (§12) is enforceable in one place per
  dependency.
- Do not build a generic plug-in framework. A port is an interface plus one
  concrete adapter; that is the whole abstraction budget for the POC.

### 2.3 Registries over conditionals

Behaviour that varies by kind is looked up, not branched on. Four registries
exist, each with a stable key, a version, and a test that asserts every entry is
reachable and documented.

| Registry | Key | Registers | Consumed by |
|---|---|---|---|
| Tool registry | `tool_name` | Callable, input schema, output schema, read/draft class, required role, audit verbosity | Orchestrator planning and execution stages |
| Index registry | `index_key` | Logical index definition, default scope eligibility, tier, freshness policy | `RetrievalScope` resolution |
| Refusal registry | `refusal_code` | Category, user-facing template, actionability hint, whether retry is meaningful | Groundedness gate, error surfaces |
| Prompt registry | `prompt_id` | Template text, template version, required variables, model compatibility | Generation and verification stages |

A new tool, index, refusal reason, or prompt is a registry entry plus a test. It
is never an `if` branch inside the orchestrator. This is what keeps the
orchestrator readable as a sequence of stages rather than a decision tree, and it
is what makes the version-pinning tuple (§11) meaningful.

### 2.4 Authorisation before the model

Scoping is a database-query predicate, applied before any candidate reaches
ranking, and long before anything reaches the model.

- The active farm lives in the authenticated server-side session and is verified
  against `FarmRole` on every scoped operation.
- `farm_id`, document state, and role-derived document eligibility are native
  `WHERE` clauses in the retrieval query. They are never applied by filtering a
  broader result set in Python.
- Owners retrieve all active documents for the selected farm. Workers retrieve
  only farm-shared safety and procedure documents plus documents linked to their
  assigned tasks.
- The model receives an already-authorised context window. There is no prompt
  instruction asking a model to respect permissions, because a prompt is not an
  access control mechanism.
- A tool that reads data re-derives scope from the request principal. It never
  accepts a `farm_id` supplied by the model as authoritative.

Post-hoc filtering is the single most common way one tenant's data reaches
another's answer. It is prohibited here, and the prohibition is enforced by test
(§13).

### 2.5 No unciteable facts

Every factual claim in an assistant response resolves to a specific retrieved
chunk or a specific structured record.

- Generation emits inline markers bound to a citation map. A claim with no marker
  is either general guidance — visibly labelled as such — or it is removed.
- Citations resolve to immutable, content-addressed chunk text, so a citation
  shown to a user in October still displays exactly what the model saw in August.
- Government-sourced citations carry a live `agriculture.gov.au` URL and are
  surfaced prominently, not buried in a footnote.
- Blended answers visually distinguish source classes: *"Per your uploaded soil
  report…"* versus *"Per DAFF guidance…"*. Mixing a farm's private data with
  public policy in one undifferentiated paragraph is a trust failure even when
  every individual claim is correct.
- If a claim fails entailment against its cited chunk, the claim is dropped,
  re-cited from another retrieved chunk, or the response degrades to a partial
  answer. It is never shipped with a citation that does not support it.

### 2.6 Audit as a stage, not as logging

Audit is a numbered stage in the orchestrator with its own failure semantics —
not a side effect scattered through the code.

- Every stage writes a structured event to an in-request audit buffer. The audit
  stage persists the buffer as one append-only record.
- The record captures the retrieval funnel (candidate IDs and scores at each
  narrowing step), the gate decision and its reason, the tools invoked and their
  arguments, the citation set with entailment scores, per-stage latency, and the
  full version-pinning tuple.
- Audit records store concise structured metadata. They do not store raw document
  bytes, and they redact secrets.
- Records are append-only for the POC lifetime. Only an owner may search or export
  them, and no deletion surface exists.
- A failure to persist an audit record is a request failure, not a warning. If the
  system cannot explain what it did, it does not get to have done it.

### 2.7 Deterministic stays deterministic

The boundary between probabilistic and deterministic components is one-way.

- FarmFlow consumes approved structured PostgreSQL data and normalised weather.
  It never consumes raw document text, retrieval output, or model output.
- The assistant may extract *candidate* rules and tasks from documents, and it may
  explain a schedule after the fact. Candidates are inert until a human approves
  them, at which point they are ordinary structured data.
- The same approved inputs must produce the same schedule proposal. Introducing a
  model anywhere inside that path breaks the guarantee and is prohibited.
- Symmetrically, deterministic tool results outrank model recall inside the
  assistant: if a tool returns a number, the response uses that number verbatim.

## 3. Runtime Shape

### 3.1 Process and store topology

```text
Browser
  │  Django pages + HTMX fragments (server-rendered HTML)
  │  DRF JSON under /api/          (tools, integrations, map data)
  ▼
Django application process  ── modular monolith
  ├─ accounts     users, roles, farm membership, permissions
  ├─ farms        farm context, places, records, weather cache
  ├─ documents    uploads, status, extraction candidates, chunk store, retrieval
  ├─ assistant    orchestrator, tool registry, citations, AI audit events
  └─ scheduling   rules, templates, tasks, schedules, FarmFlow
  │
  ├──► PostgreSQL   pgvector (embeddings) · FTS tsvector (lexical) · PostGIS (geo)
  ├──► MinIO        original document bytes, S3-compatible
  ├──► Redis        queue transport only
  └──► Ports        GenerationPort · EmbeddingPort · RerankPort · WeatherPort
  │
  └─ enqueue ─► Django-RQ worker(s) + RQ scheduler
                  extraction · chunking · embedding · candidate generation
                  weather refresh · alert evaluation · schedule proposals
```

The browser talks only to Django. It never reaches PostgreSQL, MinIO, the LLM
provider, or the weather provider directly. Workers run from the same codebase
and share the same models, ports, and service functions as the web process.

### 3.2 Why one Postgres carries three retrieval mechanisms

| Mechanism | Extension / feature | Used for |
|---|---|---|
| Dense similarity | `pgvector` | Semantic recall over chunk embeddings |
| Lexical match | Postgres FTS (`tsvector` + GIN) | Exact terms dense models lose: chemical names, machinery model numbers, standard codes, cultivar names, dates |
| Spatial | PostGIS | Farm point for weather, place boundaries for map context |

Hybrid recall is dense plus FTS fused by Reciprocal Rank Fusion. Using Postgres
FTS rather than a separate search cluster keeps the POC to one datastore, keeps
the tenant predicate in the same query plan as the similarity search (§2.4), and
keeps both halves of the hybrid transactionally consistent with document state.
An external BM25 service is the documented upgrade path if lexical quality proves
insufficient, not a day-one dependency.

### 3.3 Orchestrator stages

The assistant is a fixed, ordered pipeline. Stages are individually testable,
individually timed, and individually audited. There is no free-running agent loop
in the POC.

| # | Stage | Responsibility | Failure behaviour |
|---|---|---|---|
| 1 | **Admit** | Authenticate, resolve active farm and `FarmRole`, build `RetrievalScope`, apply rate limits | Reject with 401/403; no model call |
| 2 | **Understand** | Classify intent, resolve conversational coreference, rewrite query, detect multi-part questions | Degrade to raw query |
| 3 | **Plan** | Select tools from the tool registry given intent and role; decide whether retrieval is needed | Degrade to retrieval-only |
| 4 | **Tools** | Execute selected read tools deterministically, in-process, with scope re-derived from the principal | Per-tool failure is recorded and surfaced; never silently skipped |
| 5 | **Retrieve** | Hybrid recall inside `RetrievalScope`; dual retrieval for blended queries | Empty result is a valid outcome routed to the gate |
| 6 | **Rank** | RRF fusion → cross-encoder rerank → MMR diversity → top-k | Reranker unavailable degrades to fused order, flagged in audit |
| 7 | **Assemble** | Small-to-big parent expansion, dedup, token-budget packing, provenance preserved | Over-budget context truncates by rank, never by silent middle-drop |
| 8 | **Gate** | Score retrieval confidence, coverage, and conflict; decide `ANSWER` / `PARTIAL` / `REFUSE` | Gate errors fail closed to `REFUSE` |
| 9 | **Generate** | Produce answer with inline citation markers under a registered prompt template | Provider failure returns a service-unavailable refusal |
| 10 | **Verify** | Resolve every marker, entailment-check every cited claim, strip or downgrade failures | Verifier unavailable downgrades response confidence and flags it |
| 11 | **Audit** | Persist the append-only record with the full version tuple | Persist failure fails the request |

Stages 5–7 are skipped when Plan determines the question is answerable purely
from structured tools (for example, *"what tasks are assigned to me tomorrow?"*).
Stages 1, 8, 10, and 11 always run.

### 3.4 Synchronous versus background work

| Work | Where | Why |
|---|---|---|
| Assistant message handling | Synchronous request | User is waiting; budgeted latency |
| Document extraction, chunking, embedding | RQ job | Slow, external, retryable |
| Candidate extraction | RQ job | Slow, produces reviewable records |
| Weather refresh | RQ scheduler, every six hours | Recurring, shared across farms |
| Schedule proposal | RQ job | Long-running; returns an accepted/status reference |

Every job is idempotent. A retry updates its existing result or leaves state
unchanged; it never creates a duplicate chunk, candidate, alert, or schedule.
Durable outcomes live in PostgreSQL. Redis carries queued work only and is
treated as disposable.

## 4. Knowledge Sources

The assistant draws on four distinct classes of knowledge. They differ in
ownership, freshness, authority, and access control, and those differences drive
every composition rule in §5.

| Source | Contents | Ownership | Update pattern | Access control | Authority for | Citation style |
|---|---|---|---|---|---|---|
| **Gov corpus — Tier A** (2,250 documents) | Curated Australian government agriculture publications: ABARES insights, outlook and crop reports, land-use and forestry statistics, policy and guidance | Public, shared across all farms | Batch, snapshot-versioned | None required; `farm_id IS NULL` | General agronomic, policy, market, and regulatory guidance | Document title + section + live `agriculture.gov.au` URL |
| **Gov corpus — Tier B** (1,054 documents) | Broader government material of lower curation confidence; peripheral, older, or thinner pages | Public, shared | Batch, same snapshot | None required | Fallback only — never in the default index | Same as Tier A, plus a lower-confidence indicator |
| **Tenant documents** | Farm-uploaded PDFs and text: soil tests, chemical labels, safety and procedure documents, service records, supplier reports, contracts | Private to one farm | Continuous, event-driven on upload | **Hard `farm_id` predicate plus role-derived document eligibility** | This farm's specific situation, materials, and obligations | *"Per your uploaded \<document\> (\<date\>)"* + in-app document link |
| **Structured farm records** | Approved facts, places, animal groups, crops, machinery, tasks, task updates, rules, schedules, alerts | Private to one farm | Transactional, human-approved | Farm-scoped, role-filtered, enforced in the tool | **Operational truth** — counts, dates, assignments, status | Record-type citation with identifier and last-updated timestamp |
| **Weather** | Normalised seven-day forecast snapshots per farm | Provider-derived, farm-scoped | Refreshed every six hours; stale after twelve | Farm-scoped through the controlled tool | Forecast conditions as of a stated retrieval time | Provider name + `retrieved_at`, with an explicit staleness flag |

Tier C (1,268 documents) is not a knowledge source. It is excluded from every
index and every scope; see §10.

Notes that matter in practice:

- Tier A is the default retrieval index. Tier B enters scope only through the
  two-pass fallback in §5.1. Diluting the default index with Tier B trades
  measurable precision for marginal recall.
- Tenant documents and gov documents share one physical table but are never
  merged into one recall call for a blended question (§5.1).
- Structured farm records are *not* retrieved. They are read through typed tools.
  Embedding operational state would make counts and statuses probabilistic, which
  is exactly the failure this architecture is built to avoid.
- Weather is never invented. When no usable snapshot exists, the assistant says
  the weather constraint could not be evaluated.

## 5. Composition Rules

How the four sources combine into one answer.

### 5.1 Dual retrieval for blended questions

A blended question needs both the farm's own data and public guidance — for
example, *"is my soil pH okay for the crop I'm planning, per government
guidelines?"*

Such a question issues **two separate retrieval calls**:

1. A tenant-scoped call: `farm_id = :farm`, active documents, role-eligible.
2. An unscoped gov call: `farm_id IS NULL`, `index_key = 'gov_tier_a'`, pinned to
   the active corpus snapshot.

They merge only at context assembly, and every chunk keeps its source class
through ranking, assembly, generation, and citation rendering.

This is deliberately not a single query with a permissive `OR` predicate. One
call, one scope. The reasons:

- A single fused call lets a strong public-corpus match crowd out the farm's own
  weaker-scoring but far more relevant document, because relevance scores are not
  comparable across corpora of different size and style.
- Separate calls let each side carry its own budget, so a blended answer always
  has room for the farm's own evidence.
- A permissive predicate is one bad boolean away from a cross-farm leak. Two
  narrow predicates fail safe.

Tier B fallback is a second pass, not a widening of the first: query Tier A; if
the gate reports low confidence or insufficient coverage, re-query Tier A + B
before refusing. Tier B results are labelled at lower confidence.

### 5.2 Tools before generation

In the POC the orchestrator runs all selected tools to completion *before* the
generation stage. The model is not given a tool-calling loop.

| Property | POC (tools before generation) | Deferred (model-driven loop) |
|---|---|---|
| Tool selection | Orchestrator, from intent + registry | Model |
| Number of round trips | One | Unbounded, needs a cap |
| Latency | Predictable | Variable |
| Auditability | Complete tool set known before generation | Reconstructed from a trace |
| Failure mode | Deterministic and testable | Depends on model behaviour |

The model receives tool results as structured context alongside retrieved chunks.
It composes; it does not decide what to call. Iterative and agentic retrieval is
a Phase 11+ item with an explicit trigger (see `PLAN.md`), and would remain capped
at two to three iterations if adopted.

### 5.3 Structured outranks prose

When a structured record and a document passage disagree, the structured record
wins.

Precedence, highest first:

1. **Approved structured farm records** — operational truth.
2. **Tenant documents** — this farm's own evidence.
3. **Gov Tier A** — authoritative general guidance.
4. **Gov Tier B** — fallback guidance, lower confidence.

Applied rules:

- A count, date, status, assignment, or identifier is quoted from the tool result
  verbatim. If a document says the farm has four paddocks and the records say
  five, the answer says five.
- A disagreement is *surfaced*, not silently resolved: the answer states the
  structured value, notes that a document indicates otherwise, and cites both.
  Silent resolution is how a stale document quietly becomes operational truth.
- Public guidance never overrides a farm's own document about that farm's own
  materials or obligations. A chemical label the farm uploaded outranks a general
  publication about that chemical class.
- Weather is authoritative only as *"the forecast as of `retrieved_at`"*, never as
  a present-tense fact, and a stale snapshot carries a visible warning.
- Safety and compliance content always adds a visible warning and requests human
  verification before action, regardless of source precedence.

### 5.4 Answer shape

Every assistant response returns a consistent structure: the answer text with
inline markers, a resolved citation list tagged by source class, an explicit
facts-versus-general-guidance split, warnings, the retrieval timestamp, and any
draft or proposal payload. Drafts are inert until a human confirms them.

## 6. Corpus Snapshot Handoff

`RAG_docs` is a build-time pipeline. FarmCore is a runtime. They are joined by an
immutable, versioned snapshot artifact — never by a shared live database and never
by a manual file copy.

### 6.1 Current corpus state

| Metric | Count |
|---|---|
| Tier A documents (default index) | 2,250 |
| Tier B documents (fallback pool) | 1,054 |
| Tier C documents (excluded) | 1,268 |
| Tier A source PDFs fetched | 639 |
| Tier A PDFs with successful text extraction | 605 |
| Tier A PDFs yielding empty extraction | 34 |

The 34 empty extractions are the image-rendered-as-PDF class. They are recorded
with reason `EMPTY_EXTRACTION` and are excluded from the snapshot rather than
silently dropped — the rejection log is a reviewed artifact, because a subset of
them will be genuinely valuable content that would need OCR to recover, and OCR
is deferred.

### 6.2 Snapshot identifier

```text
snapshot_id = gov-<tier_set>-<YYYYMMDD>-<content_hash_12>

example: gov-a-20260827-9f4c1ba7e2d0
         gov-ab-20260903-3ce07a1d8b45
```

| Component | Meaning |
|---|---|
| `gov` | Corpus family. Tenant documents are never part of a snapshot. |
| `<tier_set>` | Tiers included: `a` for Tier A only, `ab` when Tier B is bundled for fallback |
| `<YYYYMMDD>` | Build date, UTC |
| `<content_hash_12>` | First 12 hex characters of a SHA-256 over the sorted chunk manifest — content-addressed, so an identical rebuild produces an identical hash |

A snapshot is immutable once published. Corrections produce a new
`snapshot_id`; they never mutate an existing one.

### 6.3 Handoff artifact

A published snapshot is a directory containing:

| File | Contents |
|---|---|
| `manifest.json` | `snapshot_id`, build timestamp, tier counts, chunker version, source-pipeline commit, extraction tool versions, document and chunk totals, embedding dimension if pre-embedded |
| `chunks.jsonl` | One JSON object per chunk: `chunk_id`, `parent_id`, `doc_id`, `text`, `tier`, `source_url`, `doc_title`, `heading_path`, `section_path`, `chunk_index_in_doc`, `token_count`, `content_hash` |
| `parents.jsonl` | Parent records for small-to-big expansion |
| `rejected.jsonl` | Every excluded document with reason code (`EMPTY_EXTRACTION`, `LIKELY_NON_TEXT_ASSET`, `NEAR_DUPLICATE`, `TIER_EXCLUDED`) and, for near-duplicates, a pointer to the retained `doc_id` |
| `checksums.txt` | SHA-256 for each file above |

`embedding` is left null in `chunks.jsonl`. Embedding happens on the FarmCore side
so the embedding model is pinned to the runtime that will query it, and so a
chunker retune does not force a re-embed of an unchanged corpus.

### 6.4 Import contract

FarmCore imports a snapshot through a management command that is idempotent and
transactional:

1. Verify `checksums.txt`; abort on any mismatch.
2. Validate every chunk against the chunk schema. Hard-fail on: any chunk over 500
   tokens, any null `source_url` or `tier`, any `parent_id` that does not resolve.
3. Insert chunks with `farm_id = NULL`, `index_key` set from tier, and
   `snapshot_id` stamped on every row.
4. Enqueue embedding jobs for the imported rows.
5. Activate the snapshot only after embedding completes for every row, by an
   atomic pointer flip in a single `corpus_snapshots` row.

Two snapshots may coexist in the table. Exactly one is active. Rollback is a
pointer flip back, which is why the previous snapshot's rows are retained until a
deliberate prune. Every audit record stores the `snapshot_id` that served it, so
any past answer can be replayed against the exact corpus that produced it.

### 6.5 Boundary rules

- FarmCore never scrapes, fetches, or re-derives corpus content at runtime.
- `RAG_docs` never connects to a FarmCore database.
- The snapshot is the only interface. A change to the chunk schema is a versioned
  contract change requiring both teams to agree.

## 7. Logical Indexes on One Physical Table

### 7.1 One table, many logical indexes

All retrievable text — government and tenant — lives in one physical
`document_chunks` table. Separation is logical, enforced by a discriminator column
and by mandatory query predicates.

```text
document_chunks
  chunk_id          uuid primary key
  parent_id         uuid           -- small-to-big expansion target
  document_id       uuid null      -- FK for tenant docs; null for gov corpus
  farm_id           uuid null      -- NULL means public gov corpus; never NULL for tenant
  index_key         text not null  -- 'gov_tier_a' | 'gov_tier_b' | 'tenant_doc'
  snapshot_id       text null      -- set for gov rows only
  tier              text null      -- 'A' | 'B' for gov rows
  doc_title         text not null
  source_url        text null      -- live gov URL; null for tenant
  heading_path      text[]
  section_path      text
  chunk_index       integer
  token_count       integer
  content_hash      text not null  -- sha256 of chunk text, content-addressed
  text              text not null
  embedding         vector(<dim>)
  text_search       tsvector generated
  doc_state         text not null  -- 'active' | 'archived'
  valid_from        timestamptz
  valid_to          timestamptz null
  superseded_by     uuid null
  created_at        timestamptz not null
```

Physical indexes:

| Index | Definition | Purpose |
|---|---|---|
| Gov dense | HNSW on `embedding` where `farm_id IS NULL AND doc_state = 'active'` | Public semantic recall |
| Tenant dense | HNSW on `embedding` where `farm_id IS NOT NULL AND doc_state = 'active'` | Farm semantic recall |
| Gov lexical | GIN on `text_search` where `farm_id IS NULL` | Public exact-term recall |
| Tenant lexical | GIN on `text_search` where `farm_id IS NOT NULL` | Farm exact-term recall |
| Scope key | B-tree on `(farm_id, index_key, doc_state)` | Predicate selectivity |
| Snapshot | B-tree on `snapshot_id` | Activation, rollback, pruning |
| Provenance | B-tree on `content_hash` | Citation resolution, dedup |

Partial indexes give the isolation benefit of separate stores — a tenant query
never traverses gov vectors, and vice versa — while keeping one schema, one
migration path, one backup, and one consistent transactional view of document
state. That last point is what a separate vector store would cost us: archiving a
document and removing it from retrieval would stop being atomic.

### 7.2 `RetrievalScope`

`RetrievalScope` is the mandatory input to every retrieval call. There is no
retrieval function that accepts a bare query string.

```python
@dataclass(frozen=True)
class RetrievalScope:
    principal_user_id: UUID
    farm_id: UUID | None            # None only for gov-only retrieval
    farm_role: Literal["owner", "worker"]
    logical_indexes: frozenset[str] # {'gov_tier_a'} | {'tenant_doc'} | ...
    doc_states: frozenset[str]      # {'active'} in the POC
    allowed_document_ids: frozenset[UUID] | None  # set for worker task-linked docs
    snapshot_id: str | None         # pinned for gov indexes
    as_of: datetime                 # freshness/supersession boundary
    top_k: int
```

Construction and enforcement rules:

- A scope is built **only** in the Admit stage, from the authenticated session and
  the verified `FarmRole`. No other layer constructs one. The model cannot
  influence any field.
- Every field becomes a SQL predicate. `farm_id`, `index_key`, `doc_state`,
  `allowed_document_ids`, and `snapshot_id` are `WHERE` clauses in the same query
  as the similarity search.
- `logical_indexes` may not mix `tenant_doc` with a `gov_*` key in a single scope.
  A blended question builds two scopes and issues two calls (§5.1). This is
  asserted at construction, not left to caller discipline.
- Worker scopes always populate `allowed_document_ids` from farm-shared
  safety/procedure documents plus documents linked to that worker's assigned
  tasks. An empty set yields an empty result and a `TENANT_SCOPE_EMPTY` refusal —
  never an unscoped fallback.
- `as_of` selects the currently valid version where supersession applies, so
  "what did the system know on date X" is answerable from the audit record.
- The scope is serialised into the audit event exactly as executed.

## 8. Request Lifecycle — `POST /api/assistant/messages`

Request:

```json
{
  "conversation_id": "uuid | null",
  "message": "Is my soil pH okay for the crop I'm planning, per government guidance?"
}
```

The active farm is **not** a request field. It is read from the server-side
session. Accepting a client-supplied farm identifier here would move an
authorisation decision to the client.

| Step | Stage | Action | Audit written |
|---|---|---|---|
| 1 | Admit | Authenticate session; load active farm; verify `FarmRole`; apply rate limit | `request.received`, principal, farm, role |
| 2 | Admit | Build `RetrievalScope`(s); resolve active `snapshot_id`; pin the version tuple | `scope.resolved`, full scope, version tuple |
| 3 | Understand | Classify intent (`operational` / `advisory` / `blended` / `weather` / `out_of_scope`); resolve coreference against current conversation; rewrite query; split multi-part questions | `query.understood`, raw + rewritten |
| 4 | Plan | Select tools from the registry filtered by intent and role; decide retrieval need and whether the query is blended | `plan.selected`, tool names, retrieval plan |
| 5 | Tools | Execute read tools in-process: farm context, tasks, approved rules, schedules, alerts, cached weather, controlled current-weather lookup. Scope re-derived from the principal per tool | `tool.invoked` per tool, args, status, latency |
| 6 | Retrieve | Dense + FTS recall per scope, RRF-fused. Blended queries run tenant and gov calls separately | `retrieval.recall` per scope, candidate IDs + scores |
| 7 | Rank | Cross-encoder rerank of fused candidates; MMR for diversity; truncate to top-k per source class | `retrieval.rerank`, ordered IDs + scores |
| 8 | Retrieve (fallback) | If the gate would fail on Tier A alone, re-query Tier A + B and re-rank once | `retrieval.fallback`, tier set, outcome |
| 9 | Assemble | Expand children to parents; dedup by `content_hash`; pack to token budget preserving source-class tags and per-class floors | `context.assembled`, final chunk IDs, token usage |
| 10 | Gate | Score retrieval confidence, coverage against every query part, and cross-chunk conflict → `ANSWER` / `PARTIAL` / `REFUSE` | `gate.decision`, scores, decision, refusal code |
| 11 | Generate | Registered prompt template; context-only constraint; inline citation markers; facts-versus-guidance separation | `generation.completed`, prompt id, token counts |
| 12 | Verify | Resolve every marker to a real chunk; entailment-check each cited claim; drop, re-cite, or downgrade failures | `verification.completed`, per-claim scores, actions |
| 13 | Audit | Persist the append-only record; failure here fails the request | `request.completed`, total latency |

Response:

```json
{
  "conversation_id": "uuid",
  "audit_id": "uuid",
  "decision": "ANSWER | PARTIAL | REFUSE",
  "refusal_code": "null | NO_RELEVANT_CONTEXT | INSUFFICIENT_COVERAGE | ...",
  "answer": "Your most recent soil test records pH 5.4 [1]. DAFF guidance ...[2]",
  "citations": [
    {
      "marker": 1,
      "source_class": "tenant_document",
      "document_id": "uuid",
      "chunk_id": "uuid",
      "title": "Soil Test — North Paddock",
      "dated": "2026-07-12",
      "entailment_score": 0.94
    },
    {
      "marker": 2,
      "source_class": "gov_tier_a",
      "chunk_id": "uuid",
      "title": "Soil acidity management",
      "source_url": "https://www.agriculture.gov.au/...",
      "snapshot_id": "gov-a-20260827-9f4c1ba7e2d0",
      "entailment_score": 0.91
    }
  ],
  "general_guidance": ["Not sourced from your farm records or the indexed corpus."],
  "warnings": [{"code": "SAFETY_VERIFY", "message": "Verify with an agronomist before application."}],
  "retrieved_at": "2026-08-27T12:04:11Z",
  "drafts": []
}
```

Refusal taxonomy, from the refusal registry:

| Code | Trigger | User-facing intent |
|---|---|---|
| `NO_RELEVANT_CONTEXT` | Nothing retrieved above threshold in any in-scope index | Say so; suggest rephrasing |
| `INSUFFICIENT_COVERAGE` | Some query parts unaddressed after Tier B fallback | Answer the covered part; state what is missing |
| `CONFLICTING_SOURCES` | Top chunks materially contradict and precedence cannot resolve | Present the conflict; do not pick silently |
| `OUT_OF_SCOPE` | Query outside the agriculture/farm-operations domain | Decline plainly |
| `ACCESS_DENIED` | Relevant content exists but the principal's role excludes it | Decline without revealing the content's existence in detail |
| `TENANT_SCOPE_EMPTY` | Question needs farm data the farm has not uploaded | Actionable: name the document type to upload |
| `PROVIDER_UNAVAILABLE` | Generation port failed after retry | Transient; retry is meaningful |

Latency budget for a blended request: Admit + Understand + Plan ≈ 400 ms, Tools
≈ 300 ms, Retrieve + Rank ≈ 800 ms, Generate ≈ 3 s, Verify ≈ 700 ms, Audit
≈ 50 ms. Stages 5–7 run concurrently with each other where dependencies allow.

## 9. Trust Boundaries

| # | Boundary | Direction | What crosses | Control | Failure if unenforced |
|---|---|---|---|---|---|
| 1 | Browser → Django | Inbound | Session cookie, form/JSON payloads | Django session auth, CSRF, DRF permissions, per-request `FarmRole` check | Unauthenticated or cross-farm access |
| 2 | Django → PostgreSQL | Outbound | Parameterised queries carrying the full `RetrievalScope` predicate | ORM parameterisation; scope built only in Admit; leak tests in CI | Cross-farm data leak |
| 3 | Django → MinIO | Outbound | Object keys, bytes, presigned URLs | Server-side key derivation; presigned URLs short-lived and farm-checked before issue | Direct object access bypassing farm scope |
| 4 | Django → Generation provider | Outbound | Prompt, already-authorised context, tool results | Context authorised upstream; secrets confined to the adapter; prompt and payload redacted in logs | Sending unauthorised content to a third party |
| 5 | Model → Tools | Inbound to FarmCore | Nothing in the POC — the orchestrator selects and executes tools | Tools before generation (§5.2); scope re-derived per tool from the principal | Model-driven privilege escalation |
| 6 | Model output → Durable state | Outbound | Drafts and proposals only | Draft lifecycle `draft → confirmed / rejected / expired`; only human confirmation writes active records | Model silently mutating operational data |
| 7 | Assistant → FarmFlow | Outbound | A proposal *request*; never a placement | Scheduler reads approved structured data only (§2.7) | Non-reproducible schedules |
| 8 | Django → Weather provider | Outbound | Farm point, forecast window | Controlled `WeatherPort`; credentials in adapter; results normalised and cached before use | Credential exposure; unbounded external cost |
| 9 | `RAG_docs` → FarmCore | Inbound | Immutable snapshot artifact only | Checksums, schema validation, atomic activation (§6.4) | Unverified content entering the corpus |
| 10 | Worker process → Everything | Outbound | Same ports and services as web | Workers reuse the same service functions and scope construction; no privileged bypass path | A background job becoming an unscoped side door |

Boundaries 2 and 5 are the two where a mistake is silent and severe. Both are
covered by mandatory tests (§13).

## 10. What Is Intentionally Not in RAG

Retrieval is a tool, not a default. The following are deliberately excluded, and
each exclusion is a design decision rather than an unimplemented feature.

| Excluded from retrieval | Why | How it is served instead |
|---|---|---|
| **Structured farm records** (tasks, schedules, rules, animal groups, machinery, places, facts) | Embedding operational state makes counts, dates, and statuses probabilistic and stale. A question like *"how many tasks are open?"* has one correct answer, retrievable exactly. | Typed read tools returning authoritative rows |
| **Gov Tier C** (1,268 documents) | Archive-grade material that dilutes precision without adding coverage. | Not indexed at all. If ever needed, a separate cold index requiring explicit human opt-in |
| **Empty-extraction PDFs** (34 of 639 Tier A) | Image-rendered PDFs yield no usable text; indexing the shell produces citations that resolve to nothing. | Logged as `EMPTY_EXTRACTION`, reviewed; recovery would require OCR, which is deferred |
| **Archived documents** | Archival exists precisely to remove content from answers while retaining it for audit. | Rows retained with `doc_state = 'archived'` and excluded by every scope |
| **Photos and images without text** | No text to embed; a caption generated by a model would be an unciteable fabrication presented as evidence. | Reference-only metadata, excluded from retrieval until a captioning path exists |
| **Raw chat history** | Conversation text is not evidence. Retrieving prior turns as if they were sources launders a model's earlier statement into a citation. | Current-conversation context is passed directly to Understand, never indexed |
| **Weather forecasts** | Time-sensitive numeric data with a hard staleness rule; semantic similarity is the wrong access mechanism. | Cached snapshots read through the controlled weather tool |
| **Audit events** | Retrieving audit records into answers would create a self-referential evidence loop. | Owner-only filtered read/export API |
| **Credentials, environment configuration, source code** | Never eligible content under any scope. | Not stored in any retrievable table |

The recurring principle: *if a question has one exact answer, retrieval is the
wrong mechanism.* Retrieval is for prose evidence with provenance. Everything with
a definite value goes through a tool.

## 11. Version Pinning

Every response is attributable to an exact configuration. The Admit stage resolves
the tuple once and stamps it on the audit record; no stage may read a different
version mid-request.

```python
@dataclass(frozen=True)
class VersionTuple:
    corpus_snapshot_id: str        # 'gov-a-20260827-9f4c1ba7e2d0'
    chunker_version: str           # 'chunk-v3'  structure-aware, 300-500 tok, 15% overlap
    embedding_model_id: str        # provider:model:revision:dimension
    retrieval_config_version: str  # 'retr-v2'  top-k, RRF weights, thresholds, MMR lambda
    reranker_model_id: str         # 'rerank-v1' or 'none'
    prompt_template_id: str        # 'answer-blended-v4'
    tool_registry_version: str     # 'tools-v5'
    generation_model_id: str       # provider:model:revision
    verifier_model_id: str         # entailment model or judge prompt id
    schema_version: str            # 'chunks-v1'  chunk record contract
```

Rules:

- The tuple is written to every audit record and returned as an opaque
  `config_fingerprint` alongside `audit_id`.
- Changing any element is a deliberate, recorded change. Evaluation results are
  only comparable across identical tuples except for the element under test.
- A quality regression is bisected by diffing tuples between a good and a bad
  audit record. This is the whole reason the tuple exists.
- `corpus_snapshot_id` and `embedding_model_id` are the two elements that require
  a reindex to change; the rest are hot configuration.
- Replay takes an `audit_id`, reconstructs the tuple and the serialised
  `RetrievalScope`, and re-executes retrieval against the pinned snapshot.

## 12. Failure Posture

Every dependency has a declared degradation. Nothing fails by fabricating.

| Dependency | Detection | Degradation | User sees | Audit |
|---|---|---|---|---|
| **Generation provider** | Timeout or error after one retry | Fail closed | `PROVIDER_UNAVAILABLE` refusal; retry is meaningful | Recorded with provider error class |
| **Embedding provider** (query-time) | Timeout or error | Fall back to FTS-only recall | Answer served with a reduced-confidence note | `retrieval.degraded = dense_unavailable` |
| **Embedding provider** (ingest-time) | Job failure | Job retries with backoff; document stays `processing` | Document status shows processing, then failed with manual retry | Job-level record |
| **Reranker** | Timeout or error | Use RRF-fused order; keep top-k | Reduced-confidence note | `retrieval.degraded = rerank_unavailable` |
| **Entailment verifier** | Timeout or error | Ship with markers resolved but claims unverified; downgrade confidence | Explicit "citations not machine-verified" note | `verification.degraded = true` |
| **pgvector similarity** | Query error | FTS-only recall | Reduced-confidence note | `retrieval.degraded = vector_error` |
| **PostgreSQL** | Connection failure | Fail closed; no cached answer path | Service-unavailable error | Best-effort local log; request fails |
| **MinIO** | Error on read/write | Uploads rejected with a clear message; retrieval unaffected because chunks live in PostgreSQL | Upload failure; chat unaffected | Document-level record |
| **Redis / RQ** | Enqueue failure | Synchronous chat unaffected; background work rejected at submission | Upload and proposal requests report unavailable | Recorded at enqueue site |
| **Weather provider** | Fetch failure | Serve the most recent snapshot | Stale warning with `retrieved_at`; FarmFlow states the weather constraint was not evaluated when no usable data exists | `weather.stale` with snapshot age |
| **No usable weather at all** | No snapshot for the farm | Do not invent values | Explicit statement that weather could not be evaluated | Recorded |
| **Corpus snapshot import** | Checksum or schema failure | Abort import; active snapshot untouched | No user impact | Import-job record |
| **Audit persistence** | Write failure | **Fail the request** | Service-unavailable error | Alerted; this is the one failure that is never degraded past |
| **Tenant scope empty** | Zero eligible documents | Not a failure — an outcome | `TENANT_SCOPE_EMPTY` with a specific upload suggestion | Recorded with scope |

Cross-cutting rules:

- **Fail closed, never fabricate.** A degraded answer is labelled; an unavailable
  system refuses. No stage substitutes parametric model knowledge for missing
  retrieval.
- **Degradations are visible.** Any downgrade appears in both the response and the
  audit record, so a quality dip is explainable after the fact.
- **Retries are bounded and idempotent.** One retry at the port level for
  synchronous work; bounded backoff for jobs. A retried job never duplicates
  state.
- **Audit outranks availability.** Every other dependency has a degradation path.
  Audit does not.

## 13. Mandatory Tests

These tests gate merge. They encode the principles that are otherwise
unenforceable by review alone.

| Test | Asserts |
|---|---|
| Cross-farm leak | For every retrieval entry point, a farm A principal never receives a farm B chunk, including under empty-result, fallback, and blended paths |
| Scope construction | `RetrievalScope` is constructible only from an authenticated principal; mixing `tenant_doc` with a `gov_*` index raises |
| No post-hoc filtering | Retrieval SQL contains the scope predicate; a static check fails on any Python-side filter of retrieval results by `farm_id` |
| Worker eligibility | A worker principal receives only farm-shared safety/procedure documents and task-linked documents |
| Citation resolution | Every marker in a generated answer resolves to a chunk in the assembled context |
| Unciteable claim | A factual sentence with no marker is either removed or labelled general guidance |
| Registry completeness | Every tool, index, refusal code, and prompt is registered, documented, and reachable |
| Gate fails closed | A gate error yields `REFUSE`, never `ANSWER` |
| Audit completeness | Every response carries an `audit_id` whose record contains the full version tuple and the executed scope |
| Job idempotency | Re-running extraction, chunking, embedding, and candidate jobs produces no duplicates |
| Snapshot import | A corrupted or schema-invalid snapshot aborts without touching the active snapshot |
| Determinism | Identical approved inputs produce an identical schedule proposal |
