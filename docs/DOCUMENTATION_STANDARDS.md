# FarmCore Documentation Standards

Writing rules, repository layout, ownership, review expectations, and templates
for the FarmCore assistant and document-retrieval track. Every contributor to this
track follows these standards.

## Document Metadata

| Field | Value |
|---|---|
| Title | FarmCore Documentation Standards |
| Status | **Accepted** |
| Date | 2026-08-27 |
| Owning team | Assistant / Documents |
| Applies to | All documentation under `docs/`, `FARMCORE_DOCS/`, ADRs, and the engineering diary |
| Enforcement | CI checks (§5); PR definition of done (§4) |

## 1. Documentation Tree

### 1.1 Repository layout

```text
RAG_docs/                              # Monorepo: ingest + assistant + data
├── README.md
├── ingest/                            # Offline corpus pipeline (scraper package)
├── farmcore/                          # Django assistant runtime (in-repo POC)
├── shared/schemas/                    # chunks-v1 and cross-track contracts
├── data/                              # Corpus on disk (manifests + pdf/text/…)
└── docs/                              # Normative FarmCore track documentation
    ├── ARCHITECTURE.md PLAN.md API.md …
    ├── adr/ openapi/
    ├── diary/Diary.md
    ├── design/DesignDoc.md
    └── product/                       # Working notes (was FARMCORE_DOCS/)
```

### 1.2 Document tiers

| Tier | Location | Authority | Update process |
|---|---|---|---|
| **Normative** | `docs/ARCHITECTURE.md`, `docs/PLAN.md`, `docs/API.md`, `docs/EXTENSIBILITY.md` | Binding for implementation | Material change → ADR + PR review |
| **Traceability** | `docs/MAPPING.md` | Links DesignDoc to FarmCore | Update in same PR as architectural change |
| **Process** | `docs/DOCUMENTATION_STANDARDS.md` | Binding for contributors | Team consensus |
| **Decisions** | `docs/adr/` | Point-in-time decisions | ADR template (§6) |
| **Diary** | `docs/diary/` | Operational log | Diary template (§7) |
| **Working notes** | `docs/product/` | Exploratory; may be stale | Promote to `docs/` when accepted |
| **Reference pattern** | `docs/design/DesignDoc.md` | General RAG pattern | Read-only reference; FarmCore specialises in ARCHITECTURE |
| **Generated** | `docs/openapi/` | API schema from code | Regenerated by CI; never hand-edited |

When `docs/product/` and `docs/` disagree, **`docs/` wins**.

### 1.3 Cross-linking rules

| Rule | Detail |
|---|---|
| Relative links within `docs/` | Use `[text](FILE.md)` |
| Links to ADRs | `[ADR-0003](adr/0003-title.md)` |
| Links to FarmCore code | Repository path in prose; no line-number links across repos |
| Upstream references | `DesignDoc.md`, `FARMCORE_DOCS/*` cited as companion, not normative |
| Version and date | Every normative doc has a metadata table with **Date** and **Status** |

## 3. Writing Rules

### 3.1 Audience and tone

| Rule | Detail |
|---|---|
| Audience | Engineers implementing FarmCore; other teams integrating against contracts |
| Tone | Direct, precise, complete sentences — not bullet-only telegraphic notes |
| Jargon | Define terms on first use in each document (`RetrievalScope`, `VersionTuple`) |
| Examples | Include JSON examples for every API request/response shape |
| Normative language | Use **must**, **must not**, **should**, **may** (RFC 2119 sense) |

### 3.2 Structure requirements

Every normative document includes:

1. **Title** — clear scope (e.g. "FarmCore API — Assistant & Knowledge Track")
2. **Metadata table** — Status, Date, Owning team, Companion records
3. **Horizontal rule** after metadata
4. **Numbered sections** — stable anchors for cross-reference
5. **Related Records** section at end

### 3.3 Content rules

| Do | Do not |
|---|---|
| State the decision and the reason | Document options without a conclusion |
| Include counts and dates when known | Use placeholder "TBD" on accepted docs without a diary entry |
| Cross-reference ADRs for disputed history | Duplicate ADR rationale in ARCHITECTURE |
| Keep API.md synchronised with DRF serializers | Hand-edit `docs/openapi/` |
| Update MAPPING.md in the same PR as architectural change | Leave traceability for a follow-up |
| Record deferred items with triggers (PLAN §11+) | Maintain an undifferentiated backlog |
| Use tables for matrices and ownership | Use nested bullet lists for tabular data |

### 3.4 Formatting

| Element | Convention |
|---|---|
| Headings | ATX style (`##`); one H1 per document |
| Code blocks | Fenced with language tag (`json`, `python`, `text`) |
| File paths | Backticks: `docs/API.md` |
| Endpoint paths | Backticks: `POST /api/assistant/messages` |
| Field names | Backticks in prose; `snake_case` in JSON |
| Dates | ISO 8601: `2026-08-27` |
| UUIDs in examples | Lowercase hex with hyphens |

### 3.5 Corpus facts (canonical as of 2026-08-27)

Use these figures consistently across all documents:

| Metric | Value |
|---|---|
| Tier A documents | 2,250 |
| Tier B documents | 1,054 |
| Tier C documents | 1,268 |
| Tier A PDFs fetched | 639 |
| Tier A PDFs text extracted | 605 |
| Tier A empty extractions | 34 |

When counts change, update every normative doc and MAPPING in one PR.

## 4. Pull Request Definition of Done

A PR touching the Assistant / Documents track is **not merge-ready** until every
applicable item below is satisfied.

### 4.1 Code changes

- [ ] Implementation matches `ARCHITECTURE.md` principles (scope in SQL, audit as stage, no post-hoc filtering)
- [ ] DRF serializers updated; OpenAPI regenerates clean
- [ ] New tools/indexes/refusals/prompts registered with version bump and test
- [ ] Mandatory tests from ARCHITECTURE §13 pass (or new test added for new behaviour)
- [ ] Cross-farm leak test passes when retrieval or documents touched
- [ ] No secrets, credentials, or raw document bytes in logs or audit payloads

### 4.2 Documentation changes

- [ ] `API.md` updated if any endpoint shape, error code, or convention changed
- [ ] `EXTENSIBILITY.md` updated if any port, registry, or extension rule changed
- [ ] `MAPPING.md` updated if DesignDoc traceability or priority changed
- [ ] `ARCHITECTURE.md` or `PLAN.md` updated if material architecture or phase scope changed
- [ ] ADR created for material decisions (§6)
- [ ] Diary entry if session produced FAILURE, DECISION, BLOCKED, or MEASUREMENT (§7)

### 4.3 Review requirements

| Change type | Required reviewers |
|---|---|
| API contract change | Assistant lead + UI representative |
| Retrieval or scope change | Assistant lead |
| Scheduling boundary | Assistant lead + Scheduling representative |
| Phase or gate change | Project lead |
| Documentation-only | One team member |

### 4.4 PR description template

```markdown
## Summary
<1–3 sentences: what and why>

## Documentation
- [ ] API.md
- [ ] EXTENSIBILITY.md
- [ ] MAPPING.md
- [ ] ARCHITECTURE.md / PLAN.md
- [ ] ADR: docs/adr/NNNN-title.md
- [ ] Diary: docs/diary/YYYY-MM-DD-slug.md
- [ ] N/A — no doc impact (<explain>)

## Tests
- [ ] Mandatory tests pass
- [ ] New test: <name or N/A>

## Gates
<List any phase gates affected: G1 scope integrity, G3 cross-farm, etc.>
```

## 5. CI Checks

Documentation and contract CI runs on every PR to the `RAG_docs` and FarmCore
repositories.

### 5.1 Documentation checks (RAG_docs)

| Check | Command / rule | Failure means |
|---|---|---|
| Markdown lint | `markdownlint-cli2 "docs/**/*.md"` | Formatting violations |
| Internal link check | `markdown-link-check` on `docs/` | Broken relative links |
| Required files exist | Assert `docs/{ARCHITECTURE,PLAN,API,EXTENSIBILITY,MAPPING,DOCUMENTATION_STANDARDS}.md` | Missing normative doc |
| Corpus fact consistency | Script compares tier counts across docs | Drift from canonical counts |
| ADR numbering | ADRs match `NNNN-*.md`; no gaps without PL sign-off | Broken ADR sequence |
| Diary date format | `docs/diary/YYYY-MM-DD-*.md` | Malformed diary filename |
| MAPPING freshness | If `ARCHITECTURE.md` changed, `MAPPING.md` must change in same PR | Traceability lag |

### 5.2 Contract checks (FarmCore repo)

| Check | Command / rule | Failure means |
|---|---|---|
| OpenAPI generation | `python manage.py spectacular --file docs/openapi/schema.yaml` | Serializer/schema drift |
| OpenAPI diff | Compare generated schema to committed; fail on breaking change unless ADR | Undocumented API break |
| Registry completeness | `pytest assistant/tests/test_registry_completeness.py` | Unregistered tool/index/refusal/prompt |
| Scope construction | `pytest documents/tests/test_scope_construction.py` | Invalid RetrievalScope allowed |
| Cross-farm leak | `pytest documents/tests/test_cross_farm_leak.py` | Tenant isolation failure |
| No post-hoc filter | Static analysis script on retrieval module | Python-side farm_id filter |
| Extraction baseline | Assert 605/639 extraction split after Phase 1 | Silent extraction regression |
| Mandatory test suite | Full ARCHITECTURE §13 test module | Principle violation |

### 5.3 Evaluation checks (from Phase 7 onward)

| Check | Rule |
|---|---|
| Regression suite | Gold-set metrics within tolerance for version tuple under test |
| Gate G12 | CI fails on regression beyond agreed threshold |

### 5.4 CI waiver process

| Situation | Process |
|---|---|
| Expected-failure placeholder (Phase 0) | Mark test `@pytest.mark.xfail(strict=True)` with phase reference |
| Temporary doc lint exception | Diary BLOCKED entry + issue link; max 7 days |
| Breaking API change | ADR + UI notification one phase ahead (gate G13) |

## 6. ADR Template

Create ADRs in `docs/adr/` with sequential numbering: `0001-short-title.md`.

```markdown
# ADR-NNNN: <Title>

## Status

Proposed | Accepted | Deprecated | Superseded by [ADR-XXXX](XXXX-title.md)

## Date

YYYY-MM-DD

## Context

<What is the issue or decision force? 2–4 paragraphs. Include constraints,
corpus facts, and which teams are affected.>

## Decision

<What is the change that is being proposed or has been agreed? State the
decision plainly. Use normative language.>

## Consequences

### Positive
- <benefit>

### Negative
- <cost or trade-off>

### Neutral
- <follow-up work>

## Alternatives Considered

| Alternative | Why rejected |
|---|---|
| <option A> | <reason> |
| <option B> | <reason> |

## Compliance

| Document | Update required |
|---|---|
| ARCHITECTURE.md | Yes / No — <section> |
| PLAN.md | Yes / No — <phase> |
| API.md | Yes / No |
| EXTENSIBILITY.md | Yes / No |
| MAPPING.md | Yes / No |

## References

- [<related doc>](path)
- [Diary entry](../diary/YYYY-MM-DD-slug.md) (if applicable)
```

### 6.1 When an ADR is required

| Trigger | ADR required |
|---|---|
| New port or fourth method on existing port | Yes |
| New retrieval stage | Yes |
| Change to scope construction rules | Yes |
| Vector store migration (pgvector → Qdrant) | Yes |
| Breaking API response shape | Yes |
| New logical index (non-obvious) | Yes |
| Editorial clarification, typo, count update | No |
| New tool registry entry | No (document in EXTENSIBILITY + API) |
| Calibrated threshold change | No (diary MEASUREMENT entry sufficient) |

## 7. Diary Entry Format

Engineering diary entries live in `docs/diary/YYYY-MM-DD-short-slug.md`. One entry
per significant session or outcome. Multiple entry types may appear in one file.

### 7.1 File template

```markdown
# Diary: YYYY-MM-DD — <Short title>

**Author:** <name>
**Team:** Assistant / Documents
**Phase:** <current phase, e.g. Phase 4>
**Related:** [<PR or issue>](url), [ADR-NNNN](../adr/NNNN-title.md)

---

## <ENTRY_TYPE>: <Headline>

**Time:** HH:MM (timezone)
**Tags:** `retrieval`, `corpus`, `gate`, etc.

<Body: 1–5 paragraphs. Factual, specific. Include numbers, decisions, blockers.>

**Follow-up:** <next action or "none">

---
```

### 7.2 Entry types

Use exactly one of these type labels per section:

#### FAILURE

Something broke, regressed, or failed a gate.

Required content:
- What failed (test name, endpoint, pipeline stage)
- Observed vs expected behaviour
- Root cause if known; hypothesis if not
- Impact (blocks phase exit? degrades demo?)
- Remediation plan

Example:

```markdown
## FAILURE: Reranker timeout pushes retrieval past 800 ms budget

**Time:** 14:30 AEST
**Tags:** `retrieval`, `latency`

Cross-encoder rerank on 50 candidates averages 1.2 s on dev hardware, exceeding
the ARCHITECTURE §8 budget of 800 ms for Retrieve + Rank combined. Dense + FTS
recall alone is 380 ms.

**Follow-up:** Cap rerank input at 30 candidates; remeasure before Phase 4 exit.
```

#### DECISION

A choice was made that does not require a full ADR.

Required content:
- Options considered (brief)
- Choice and rationale
- Documents to update

Example:

```markdown
## DECISION: Provisional RRF weights 1.0 / 1.0 until Phase 7 gold set

**Time:** 11:00 AEST
**Tags:** `retrieval`, `config`

Equal RRF weights for dense and lexical chosen for Phase 4 initial merge.
Final tuning deferred to Phase 7 regression suite.

**Follow-up:** Record baseline metrics in Phase 4 exit; note in MAPPING.md (done).
```

#### PROGRESS

Milestone reached or deliverable completed.

Required content:
- What was completed
- Exit criteria met (yes/no/partial)
- Metrics if applicable

Example:

```markdown
## PROGRESS: First gov-a snapshot published

**Time:** 16:45 AEST
**Tags:** `corpus`, `snapshot`

Snapshot `gov-a-20260827-9f4c1ba7e2d0` built from 605 extracted Tier A documents.
48,200 chunks; validation gates pass; checksums committed.

**Follow-up:** Phase 3 import command (in progress).
```

#### BLOCKED

Work cannot proceed without external input.

Required content:
- Blocker description
- Who unblocks
- Workaround if any

Example:

```markdown
## BLOCKED: Embedding dimension blocks pgvector migration

**Time:** 09:15 AEST
**Tags:** `embedding`, `schema`

Cannot migrate `embedding vector(n)` until model selected and dimension confirmed.
Phase 3 entry criteria unmet.

**Follow-up:** PL sign-off on bge-large-en-v1.5 (1024 dim) expected Friday.
```

#### MEASUREMENT

Quantitative observation; no decision implied.

Required content:
- Metric name and value
- Version tuple or config under test
- Comparison to baseline if available

Example:

```markdown
## MEASUREMENT: Hybrid + rerank Recall@5 = 0.71 vs dense-only 0.58

**Time:** 17:00 AEST
**Tags:** `eval`, `retrieval`

Gold set v0 (42 queries, informal labels). Version tuple: retr-v2, gov-a-20260827.
MRR@5: 0.64 → 0.76.

**Follow-up:** Formal Phase 7 harness; do not tune weights on this sample.
```

#### NOTE

General observation worth recording; does not fit other types.

Required content:
- Observation
- Why it matters (one sentence)

Example:

```markdown
## NOTE: 12 of 34 empty extractions are multi-page scanned reports

**Time:** 10:30 AEST
**Tags:** `corpus`, `ocr`

Manual review of empty extraction sample suggests OCR trigger evidence exists
but not yet at the Phase 11+ threshold.

**Follow-up:** none
```

### 7.3 Diary rules

| Rule | Detail |
|---|---|
| Filename | `YYYY-MM-DD-slug.md`; slug is lowercase kebab-case |
| One file per day preferred | Multiple entry types in one file allowed |
| Link to ADR | When DECISION is ADR-worthy but ADR deferred |
| No secrets | Never record credentials, API keys, or PII |
| Corpus counts | MEASUREMENT entries cite version tuple when eval-related |

## 8. OpenAPI and API.md Synchronisation

| Source of truth | Consumer |
|---|---|
| DRF serializers (FarmCore repo) | Generated `docs/openapi/schema.yaml` |
| `docs/API.md` | Human-readable normative contract |

Rules:

1. Serializers define field names, types, and validation.
2. CI regenerates OpenAPI on every FarmCore PR.
3. `API.md` is updated in the same PR when endpoints change.
4. Breaking changes require ADR and UI notification one phase ahead (gate G13).
5. `GET /api/capabilities` reflects live registry and feature flags.
